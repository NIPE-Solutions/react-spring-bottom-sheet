# React Spring Bottom Sheet v4.1 Stabilization

## Purpose

Revive the project with a non-breaking `4.1.0` release that existing users can adopt safely. This milestone establishes reliable maintenance infrastructure, fixes confirmed defects, verifies the existing React 16.14 through 18 support range, and prepares the repository for a later breaking `5.0.0` modernization.

Version 4.1 will not migrate the animation, gesture, or state-machine foundations to new major versions. Those changes belong in version 5 after the existing behavior is protected by tests.

## Compatibility Contract

Version 4.1 must preserve:

- The `BottomSheet`, `BottomSheetProps`, and `BottomSheetRef` exports.
- Existing component props, callback event shapes, defaults, and ref methods.
- CommonJS and ES module entry points used by existing consumers.
- The documented `dist/style.css` and `defaults.json` imports.
- Verified compatibility across the existing React 16.14 through 18 support range.
- Current observable animation and gesture behavior except where it is demonstrably defective or inaccessible.

Adding optional accessibility props, package export metadata, tests, or stricter internal types is non-breaking. Correcting behavior that contradicts the existing documentation is also considered a compatible bug fix and must be covered by a regression test.

## Workstreams

### 1. Honest Quality Gates

Replace the current build-only `test` command with separate, composable checks:

- Unit and component tests run in a DOM-like test environment.
- Browser tests exercise the included fixtures in a real browser.
- Linting fails on warnings.
- Type checking runs independently for library and documentation code.
- The distributable library and documentation site build independently.
- Package validation inspects the packed tarball and verifies public entry points.

GitHub Actions will run these checks for pull requests and pushes to the main branch. The compatibility matrix will cover supported Node LTS releases and React 16.14, 17, and 18 where a React-specific consumer test is relevant.

Warnings produced by project-owned configuration or source code are failures. Third-party warnings that cannot immediately be removed must be documented and isolated rather than silently accepted.

### 2. Regression Test Foundation

Use Vitest and Testing Library for fast unit and component coverage. Use Playwright for browser behavior that depends on layout, focus, scrolling, pointer input, or animation timing.

Initial automated coverage must include:

- Snap-point normalization, clamping, deduplication, and invalid input.
- Controlled and viewport-derived maximum height.
- Opening, closing, unmounting, and reopening.
- Escape and backdrop dismissal.
- Initial focus, focus containment, and focus restoration.
- Blocking and non-blocking accessibility semantics.
- Synchronous and asynchronous spring lifecycle callbacks.
- Snap commands through `BottomSheetRef`.
- Rapid open/close changes and interrupted transitions.
- Reduced-motion behavior.
- At least one drag-to-snap and one content-scroll scenario in a real browser.

Tests should assert observed public behavior. Internal XState snapshots may be tested only where they are themselves exposed through the documented `data-rsbs-state` DOM contract.

### 3. Confirmed Correctness Fixes

The first stabilization release will address these evidenced defects:

- Initialize a controlled `maxHeight` from the prop instead of initially substituting `window.innerHeight`.
- Ensure a changed `springConfig` is used by subsequent animations.
- Make lifecycle callbacks consistently await returned promises, matching the documentation.
- Update callback types to accept `void | Promise<void>` without changing their event arguments.
- Derive `data-rsbs-state` correctly for nested XState states.
- Remove `aria-modal="true"` from non-blocking sheets while retaining modal semantics for blocking sheets.
- Add an accessible naming path through normal dialog ARIA attributes without requiring a new mandatory prop.
- Remove development diagnostics that currently flood the console.

Rapid transitions will be characterized with tests before cancellation behavior is changed. If reliable cancellation requires a public semantic change, that work will move to version 5 rather than expanding version 4.1.

### 4. Build and Documentation Repair

Version 4.1 will produce clean output from a fresh install by repairing:

- The Microbundle TypeScript declaration configuration error.
- The incompatible PostCSS/SVGO integration.
- Obsolete Tailwind configuration and color names.
- The unnecessary Babel configuration that disables Next.js SWC, if removing it does not change library output.
- The invalid documentation `<title>` composition.
- Dead imports, dead XState types, TypeScript suppressions that can be removed safely, and current lint failures.

The documentation application remains a development and demonstration surface, not part of the runtime library. Its dependencies and configuration must not leak into the published runtime dependency graph.

### 5. Packaging and Dependency Hygiene

Add a package `exports` map for:

- The package root, including JavaScript and TypeScript declarations.
- `./dist/style.css` for backward compatibility.
- `./style.css` as the preferred stable stylesheet subpath.
- `./defaults.json`.

Retain legacy `main`, `module`, `jsnext:main`, `types`, and `style` fields in version 4.1. Validate both `require()` and `import` consumption from a packed tarball.

Move PostCSS and SVG processing packages to development dependencies and upgrade them to non-vulnerable compatible releases. Remove generated build metadata such as TypeScript `.tsbuildinfo` files from the tarball. Review every runtime dependency and keep only code needed by consumers.

Version 4.1 will take compatible dependency updates, but not major upgrades of React Spring, the gesture library, or XState React. Security issues that cannot be eliminated without such a migration must be documented explicitly and prioritized for version 5.

### 6. Repository Maintenance

Replace the inherited Renovate preset with repository-owned configuration. Dependency automation will:

- Open security updates promptly.
- Group low-risk development-tool updates.
- Keep runtime major upgrades separate and require manual review.
- Avoid automatic merging of changes that affect shipped behavior.

Add contributor-facing commands and a release checklist to the repository documentation. The release process must require a clean CI run and packed-package validation before publication.

## Internal Structure

Version 4.1 will favor targeted extraction over a broad rewrite. Pure snap-point and state-derivation logic may move into focused utility modules so it can be tested without mounting the complete component. Accessibility, animation, measurement, and gesture behavior will otherwise remain behind the current component boundary.

The large `BottomSheet` component will not be comprehensively redesigned in this milestone. Version 5 will reconsider its boundaries after the regression suite describes the behavior that must be retained.

## Version 5 Boundary

The following are explicitly deferred to the `5.0.0` design:

- Major React Spring and gesture-library migrations.
- A full XState machine rewrite or removal.
- Removal or renaming of public props and exports.
- Dropping older browser behavior or changing the browser support policy.
- Replacing animation semantics, snap physics, or dismissal thresholds.
- Redesigning portal ownership, controlled state, or imperative APIs.
- Removing legacy package entry fields.

The v5 design will use the v4.1 regression suite as its compatibility baseline and will document every intentional breaking change.

## Completion Criteria

Version 4.1 is release-ready when:

1. A clean install completes without known vulnerabilities in shipped runtime dependencies.
2. Lint, type checking, unit/component tests, browser tests, library build, and documentation build all pass without project-owned warnings.
3. Packed-package tests pass against React 16.14, 17, and 18.
4. The packed tarball contains only intended files and works in CommonJS and ES module consumer fixtures.
5. Confirmed correctness and accessibility defects have regression tests.
6. Public APIs and legacy import paths remain compatible.
7. The changelog and migration notes state that no consumer migration is required.

## Delivery Strategy

Work will be divided into independently reviewable changes: test infrastructure, pure-logic regressions, component behavior regressions, accessibility, build repair, packaging, CI, and documentation. Each behavior change follows a red-green-refactor cycle. Major dependency upgrades will not be bundled with behavior fixes, keeping regressions attributable and reversions practical.
